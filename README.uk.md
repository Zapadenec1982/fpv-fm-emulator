# FPV FM-емулятор для Pluto+

[English](README.md) | **Українська**

Генератор тестового **аналогового FPV-відеосигналу з ЧМ-модуляцією** на базі SDR
**ADALM-Pluto+**. Формує реалістичне композитне відео (кольорові тестові таблиці),
частотно модулює ним несучу й випромінює в ефір — щоб перевіряти роботу **детекторів
аналогового FPV** за різними діапазонами, каналами, потужностями та сценаріями (свіп
по діапазонах, рамп потужності, кілька «дронів» одночасно) або вручну.

![Головне вікно програми](docs/screenshot.png)

> Це **стендовий генератор тестового сигналу**. Веде передачу в радіоефір —
> використовуйте лише в екранованому середовищі / на дозволених частотах, з
> відповідними погодженнями. Відповідальність за роботу в ефірі — на операторі.

## Що воно робить

Реальний аналоговий FPV-передавач частотно модулює несучу композитним відео з
камери. FPV-детектор приймає це ЧМ-відео й виявляє присутність дрона. Емулятор
відтворює саме такий сигнал:

```
кольорова тест-таблиця → композитне відео (CVBS, PAL50/NTSC60) → ЧМ → IQ → Pluto TX
```

**Важливо (перевірено на реальному детекторі):** детектор дивиться не лише на
потужність (RSSI), а на **профіль модуляції**. Тому за замовчуванням генерується
**реалістичний FPV-профіль** — кольорові смуги з піднесучою 4.43 МГц + широка ЧМ,
зайнята смуга ~17 МГц, як у справжнього VTX. Вузький ч/б давав високий RSSI, але
розпізнавався погано.

## Архітектура

Ядро не залежить від апаратури — його можна запускати й тестувати офлайн.

```
fpv_emulator/

  signal_gen.py   відео+ЧМ → кадровий (циклічний) IQ; мультидрон
  backends.py     приймачі IQ: Pluto (pyadi-iio) | hackrf | soapy (HackRF/Lime/…) | file | null
  hackrf.py       HackRF One через libhackrf (ctypes) + його проба
  scenarios.py    рушій сценаріїв (static/sweep+pause/power_ramp/multi_drone), жива потужність
  config.py       завантаження/валідація YAML-сценаріїв
  probe.py        визначення чипа й меж перестроювання Pluto
  iio_layout.py   шукає IIO-пристрої керування/RX/TX за формою, а не за іменем
  iio_host.py     libiio на цьому компʼютері; пояснює словами, чому плата не відкрилась
  firmware.py     профілі прошивки (які способи задання частоти дозволено пробувати)
  i18n.py         каталог English/Українська
  cli.py          командний інтерфейс
gui/app.py        десктоп-GUI (PySide6): ручне керування + сценарії + прев'ю
config/
  bands.yaml      частоти каналів (редаговані)
  scenarios/*.yaml приклади сценаріїв
scripts/probe_pluto.py   автономна проба апаратури
CHANGELOG.md      що змінилось у кожній версії
tests/            офлайн-тести ядра (pytest, 209 шт.)
```

## Встановлення та запуск (Windows — два кліки)

**Головний інструмент — GUI.** Термінал для роботи не потрібен:

1. **`setup.bat`** — подвійний клік **один раз**. Створить оточення `.venv` і поставить
   усе потрібне (numpy, PySide6, pyadi-iio…).
2. **`run_gui.bat`** — подвійний клік, щоб **запустити GUI**. Відкриється головне
   вікно (помилки старту, якщо є, покаже діалог).

> **Для передачі через Pluto Windows потрібні ще два інсталятори від Analog Devices,
> один раз на компʼютер** — `setup.bat` їх не поставить, а після перевстановлення
> Windows вони потрібні знову: [USB-драйвери Pluto](https://github.com/analogdevicesinc/plutosdr-m2k-drivers-win/releases)
> (`PlutoSDR-M2k-USB-Drivers.exe`) і **libiio 0.25** (файл `…-setup.exe` на
> [сторінці її релізу](https://github.com/analogdevicesinc/libiio/releases/tag/v0.25)).
> Беріть саме 0.25, а не новішу 1.x: Python-частина, яку ставить `setup.bat`, написана
> під 0.x. «Проба Pluto» скаже, чого з двох бракує. Якщо плата підключена, а
> `ip:192.168.2.1` не відповідає, URI `usb:` дістанеться до неї напряму через USB.

> Порада: правий клік на `run_gui.bat` → створити ярлик на робочому столі / закріпити
> на панелі задач — і запуск буде в один клік.

### GUI — що всередині

Відкривається одразу з робочим профілем (color_bars, 20 MSPS, PAL50, backend
`pluto`). Усе керується мишкою:
- **Вихід:** backend (`pluto` / `hackrf` / `soapy` для інших SDR), URI/пристрій, профіль
  **Прошивки** (див. нижче), кнопки «Проба Pluto» і «Список SDR».
- **Частота:** банд/канал або несуча вручну.
- **Сигнал:** стандарт, патерн (прев'ю в кольорі), частота дискретизації, девіація.
- **Потужність:** повзунок, **міняється в рантаймі** під час передачі.
- **Режим:** ручна несуча або готовий сценарій; Старт/Стоп; журнал подій із
  перемикачем **«Детально»** — коли вимкнено, нотатка про те, як довелося
  налаштувати плату, зʼявляється раз за сеанс, а не на кожному Старті.
- **Мова:** перемикач у панелі **«Вихід»** змінює мову інтерфейсу
  (English / Українська).

**Вікно відкривається там, де ви його лишили.** Усі налаштування — backend, URI,
діапазон і канал, несуча, стандарт, патерн, частота дискретизації, девіація,
потужність, профіль прошивки, режим і мова — зберігаються при закритті вікна й при
натисканні «Старт», і відновлюються на наступному запуску. Журнал подій не
зберігається: вчорашній лог у свіжому вікні читається так, ніби він від цього
сеансу. Збережене значення, якого вже немає (перейменований патерн, прибраний із
`bands.yaml` діапазон), тихо відкидається, а віджет лишається на своєму типовому.

Для передачі: оберіть backend `pluto` (або `soapy`), частоту → **Старт**.

## Термінал (CLI) — лише для автоматизації

GUI покриває щоденну роботу; CLI зручний для скриптів. Запуск — через `.venv`:

```bash
.venv\Scripts\python.exe -m fpv_emulator.cli probe
.venv\Scripts\python.exe -m fpv_emulator.cli tx --backend pluto --scenario sweep_ranges
.venv\Scripts\python.exe -m fpv_emulator.cli tx --backend pluto --freq-mhz 1200 --pattern color_bars --gain 0
.venv\Scripts\python.exe -m fpv_emulator.cli gen --pattern color_bars --sample-rate 20e6 --out frame.iq
.venv\Scripts\python.exe -m fpv_emulator.cli list-bands   # також list-patterns | list-scenarios | list-devices
```

Мова інтерфейсу обирається прапорцем `--lang en|uk` (за замовчуванням англійська);
змінна оточення `FPV_LANG=uk` працює як запасне значення за замовчуванням.
`--firmware` задає профіль прошивки (див. нижче).

Ручне встановлення (замість `setup.bat`):
```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt -r requirements-hw.txt
```
Нативна **libiio** має бути в системі (Windows: libiio 0.25 від Analog Devices, див.
вище; Linux: `apt install libiio0 libiio-utils`).

## Відеостандарти й патерни

**Стандарти:** `PAL50` (312 рядків, 50 Гц поля) і `NTSC60` (262 рядки, 60 Гц) —
прогресивні 288p/240p. Саме частота полів 50/60 Гц (а не 25/30) прибирає
вертикальний зсув картинки на моніторі детектора. Старі імена `PAL`/`NTSC`
автоматично мапляться на `PAL50`/`NTSC60`.

**Люма-патерни (ч/б):** `bars`, `smpte75`, `ramp`, `crosshair`, `grid`, `checker`,
`multiburst`, `white`, `gray`, `black`.

**Кольорові патерни (реалістичний FPV):** `color_bars` (75%), `color_bars100` —
з піднесучою 4.43 МГц (PAL) / 3.58 МГц (NTSC), burst і чрома-модуляцією. Нижче
`fs = 2.2 × піднесуча` (~9.8 MSPS для PAL) піднесуча аліасить і виклик відхиляється;
**рекомендовано 13–15 MSPS**, а GUI відкривається на 20.

## Сценарії (YAML)

Спільний блок `signal:` (standard, pattern, sample_rate, deviation_pp_hz, gain_db),
далі блок за типом. Приклади — у `config/scenarios/`.

| Тип | Призначення |
|-----|-------------|
| `static` | одна несуча (channel/freq_mhz, hold_s) |
| `sweep` | перебір каналів/**діапазонів з кроком** (`ranges`), з опційною **паузою** (`pause_s`) |
| `power_ramp` | наближення/віддалення дрона (start_db→end_db, mode: up/down/pingpong) |
| `multi_drone` | кілька несучих одночасно (drones[{pattern, offset_mhz, level_db}]) |

**Рознесення в мультидроні.** Одна реалістична FPV-несуча займає ~11.5 МГц на рівні
−30 дБ, тож дві несучі, ближчі за **~14 МГц**, зливаються в одну широку пляму й
детектор бачить одну ціль замість двох (провал між піками падає до ~16 дБ). У
штатному сценарії — **18 МГц** (зсуви ±9), де провал ~36 дБ, а за Найквіст
завертається лише 0.34 % потужності. Стеля — сама плата, не інструмент: Pluto+ тримає
максимум **30.72 MSPS** (40 / 50 / 61.44 відхиляються з errno 22, і вимкнення TX FIR
цього не змінює), що обмежує рознесення ~20 МГц — тоді як Nano на прошивці Tezuka
приймає **61.44 MSPS**, де ~32 МГц влазять із запасом. Штатний сценарій лишається на
30.72, щоб працював на обох. Ближчі зсуви дають попередження, а не помилку.

Свіп за діапазонами:
```yaml
sweep:
  ranges:
    - { start_mhz: 5650, stop_mhz: 5950, step_mhz: 20 }   # напр. 5.8 ГГц FPV
  dwell_s: 15    # передача на частоті
  pause_s: 5     # тиша (RF off) між частотами
```

## Як це працює (DSP)

1. **Композитне поле** (`video.py`): один період поля 288p/240p із коректним
   таймінгом рядків і вертикальним синхро (50/60 Гц). Для кольору додається
   піднесуча + burst + чрома (U/V; для PAL — перемикання фази V по рядках).
2. **ЧМ** (`fm.py`): `iq = exp(j·2π·∫ dev·v dt)`. Центрування (віднімання середнього)
   забезпечує фазову неперервність на стику циклічного буфера.
3. **Циклічний буфер**: одне поле вантажиться як `tx_cyclic_buffer` і повторюється
   в пристрої. Зміна частоти/потужності — на льоту; зміна патерну — перезаливка.
4. **Жива потужність**: слайдер у GUI кладе значення, а робочий потік застосовує
   `tx_hardwaregain` (libiio чіпається лише з одного потоку).

**Найквіст:** пікова екскурсія `±девіація/2` (+зсуви мультидрону) має бути < `fs/2`,
інакше сигнал завертається (є попередження).

## Профілі прошивки

Зверніть увагу: це інша вісь, ніж таблиця вище. Там — *діапазон перестроювання чипа*
(слова «стоковий» і «мод», а також поле «HW range» у GUI), тут — *прошивка на платі*.

Задання частоти дискретизації через pyadi — це `ad9361_set_bb_rate()` з libad9361,
яка не лише ставить частоту: вона ще вантажить інтерполяційний FIR-фільтр і вмикає
його. Pluto+ зі стоковою прошивкою Analog Devices це приймає. Nano PlutoSDR із
`tezuka-v0.3.141592653` відмовляє голим `[Errno 22] Invalid argument`, водночас
публікуючи 2.083–61.44 MSPS як доступні — а це саме той діапазон, який AD9361 має з
*вимкненим* FIR. Частота ніколи не була проблемою.

Профіль каже, що емулятору дозволено **пробувати**, а не чим є плата:

| Профіль | Поведінка | Коли |
|---------|-----------|------|
| **Авто** (типово) | Пробує шлях pyadi з фільтром; якщо плата відмовила — ставить частоту з вимкненим FIR і повідомляє про це | Завжди, якщо немає причини інакше. Правильний для обох плат |
| **Analog Devices** | Лише шлях pyadi — відмова є помилкою, а не приводом до відкату | Щоб довести, що плата справді не приймає фільтр |
| **Tezuka** | Ставить частоту з вимкненим FIR, без невдалої спроби перед цим | Щоб прибрати відому плату зі шляху невдалого запису, напр. під час вимірювань часу |

GUI: поле **«Прошивка»** в панелі *«Вихід»*. Вибір запамʼятовується між сеансами, а
примусовий пишеться в журнал подій на кожному Старті — липке перевизначення, яке
тихо переїхало б з іншою платою на стенд, було б гіршим за баг, який воно обходить.

CLI: `--firmware auto|adi|tezuka`, для кожної команди, що відкриває пристрій. Немає
для `probe`, який ніколи не задає частоту дискретизації — прапорець там парсився б і
нічого не змінював. Натомість `probe` **повідомляє** знайдену прошивку.

Автовизначення свідомо не обирає гілку коду. «Tezuka» — це *збірник* прошивок
приблизно для десятка різних плат, тож рядок версії не передбачає, чи прийме плата
фільтр; а запит до плати — передбачає. Те, що читається з `fw_version`, слугує лише
для підпису плати й попередження, коли ручне перевизначення цьому суперечить.

Відмова від FIR коштує частини придушення дзеркал обабіч смуги. На саме відео це не
впливає, зайнята смуга не змінюється.

## Підтримувані SDR

Ядро генерує IQ незалежно від апаратури; передавальний бекенд обирається прапорцем
`--backend` (CLI) або у GUI.

| Backend | Пристрої | Примітки |
|---------|----------|----------|
| `pluto` | ADALM-Pluto / Pluto+ | нативно (pyadi-iio/libiio), циклічний буфер у пристрої |
| `hackrf` | **HackRF One** | нативно (libhackrf, без SoapySDR); кадр крутить хост |
| `soapy` | **HackRF, LimeSDR, BladeRF, USRP**, Pluto та ін. | через SoapySDR; хост безперервно ллє кадр |
| `file` | будь-який (офлайн) | запис IQ у `.iq`/`.npy` |
| `null` | — | сухий прогін без ефіру |

SoapySDR-приклади:
```bash
python -m fpv_emulator.cli list-devices                       # знайти підключені SDR
python -m fpv_emulator.cli tx --backend soapy --device driver=hackrf --freq-mhz 5800 --gain 0
python -m fpv_emulator.cli tx --backend soapy --device driver=lime --scenario sweep_ranges
```
У GUI: backend `soapy`, у полі «SDR (soapy)» — `driver=hackrf|lime|uhd|bladerf`,
кнопка «Список SDR» покаже доступні. Потужність (слайдер −89..0, 0 = макс)
автоматично мапиться на реальний діапазон підсилення пристрою.

**Нюанси:** HackRF — 8 біт, напівдуплекс, макс ~20 MSPS, немає апаратного циклічного
буфера (хост крутить кадр). Дешеві RTL-SDR-донгли **передавати не вміють** (тільки
прийом). Діагностики через RX (проба, RX-самоприйом) — специфічні для Pluto.
Встановлення SoapySDR — див. `requirements-hw.txt` (pip його не ставить).

### HackRF One (`hackrf`)

Напряму через libhackrf — без SoapySDR. У Windows бібліотеку треба один раз завантажити:
```bash
python scripts/fetch_hackrf.py          # кладе hackrf-0.dll + libusb + libwinpthread у third_party/hackrf
python -m fpv_emulator.cli probe --device hackrf
python -m fpv_emulator.cli tx --backend hackrf --channel R1 --gain -20
python -m fpv_emulator.cli tx --backend hackrf --freq-mhz 4500 --gain 0 --amp
```
(Linux: `apt install libhackrf0`. `HACKRF_LIB` задає бібліотеку явно.) Драйвер HackRF —
WinUSB; зі свіжою прошивкою HackRF Windows ставить його сама.

У GUI: backend `hackrf`, за потреби серійник плати (порожньо = перша знайдена) і
перемикач **RF-підсилювач +14 дБ**; «Проба HackRF» читає плату, прошивку й серійник.
Відмінності від Pluto:
- частота дискретизації **2–20 MSPS** (типові 20 підходять), IQ 8 біт;
- потужність: один дБ повзунка — це один дБ в ефірі від максимуму — 0..−47 дБ (TXVGA),
  з підсилювачем 0..−61 дБ; він вмикається лише коли самого TXVGA не вистачає.
  Ніколи не вмикайте підсилювач без антени чи навантаження;
- кадр крутить хост; зупиняйте кнопкою **Стоп** (або Ctrl+C). Процес, убитий посеред
  передачі, може лишити плату в режимі TX — тоді вона відповідає «не знайдено», доки не
  натиснути **RESET**.

## Версія

Одне число, у `fpv_emulator/__init__.py`, показується в заголовку вікна, першим
рядком журналу подій, у діалозі помилки запуску, зверху виводу `probe` і через
`--version`. Якщо щось поводиться дивно — це перше, що варто назвати: сенс саме в
тому, щоб відповісти «яка це збірка?» зі скріншота.

Що змінилось — у [CHANGELOG.md](CHANGELOG.md) (англійською). Тест падає, якщо версія
й найновіший запис у changelog розходяться, тож розійтися вони не можуть.

## Тести
```bash
python -m pytest tests/ -q
```
209 офлайн-тестів, апаратура не потрібна. Покривають: пошук бендів/каналів (зокрема
неоднозначні «голі» імена), guard за межами HW, таймінг і рівні композитного відео,
кольоровий тракт (піднесуча, розміщення burst, чергування фази V у PAL), інваріанти
ЧМ і неперервність стику циклічного буфера, сумування мультидрону та рознесення його
несучих, попередження про аліасинг, прогони рушія сценаріїв на записувальному
приймачі (свіп, пауза з RF off, порядок «спершу перестроїти, потім старт», рамп
потужності, жива потужність), визначення розкладки IIO на платах із власними іменами
пристроїв, шлях задання частоти дискретизації для кожного профілю прошивки, те, що
`--firmware` справді доходить до кожного відкриття пристрою, те, що плату ніколи не
тримають два контексти одночасно (USB-плата приймає лише один), те, що відсутня
libiio і плата, яка не відповідає, описуються словами, а не шумом ctypes та errno,
те, що український каталог покриває кожен рядок, який показують код і штатні YAML,
і те, що збережений стан вікна переживає перезапуск (зокрема значення, на яких
наївне відновлення помиляється: чекбокс «false», діапазон, збережений за позицією,
застарілий патерн).

## Ключові висновки
- **RSSI ≠ якість прийому.** Детектор дивиться на профіль модуляції → реалістичний
  широкий кольоровий сигнал розпізнається, вузький ч/б — ні, попри високий RSSI.
- Кадрова **50/60 Гц полів** (не 25/30) — обовʼязкова для правильної вертикальної
  синхронізації на моніторі детектора.
- **Більше потужності ≠ краще.** У діапазоні 1.2 ГГц найкращі результати дали
  **−30 дБ**. На −10 дБ підсилювач входить у компресію: зʼявляються гармоніки, які
  теж несуть відео, детектор може сісти на одну з них, а на основній частоті буде
  чорний екран — при тому, що РЧ на аналізаторі явно присутня.
- **Передавач може відзвітувати про успіх і мовчати.** `tx()` повертається без
  помилки, а DMA так і не стартує. Приймач IQ перевіряє це цифровим лупбеком і
  повторює спробу, бо все, що міряється нижче за непоміченого мовчазного
  передавача, — хибне.
